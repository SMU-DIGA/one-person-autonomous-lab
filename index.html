OPAL

One-Person · Autonomous · Lab

面向计算型研究的责任与证据控制面：一个人、N 个自主 agent，以及一套使规模化研究执行可分配、可追踪、可核验、可问责的基础设施。

治理不是对速度的限制。它是自主执行得以放开规模的前提条件。

One-Person责任的计量单位。系统最终服务于一个充分理解并愿意签署的人，而非制造无人负责的自动化。
Autonomous执行的形态。Agent 在可执行的 contract 边界内自主迭代，无需逐步批准；越界即停止，而非事后补报。
Lab组织的形态。具备预算纪律、证据链、失败记忆与可复利资产，而非一个对话工具。

01

定位：优先解决计算型研究的责任问题

OPAL 是面向计算型研究的责任与证据控制面，首期覆盖模型训练、算法实验、仿真、数据分析、benchmark 等可通过代码、数据快照与运行环境重放的工作流。

它不试图替代 scientific taste，也不主张可以从 provenance 推导出科学真理。其目标是把自主执行转化为一种可由单个研究者可靠监督的组织形态：资源有上限，行为有边界，结论有来源，异常会停止，最终责任落在签名上。

In scope

可代码化、可重放的研究执行

代码、数据、配置、环境、run、artifact、自动 gate、claim 与签署之间的完整关联。

Out of first scope

无法完整数字化的实验活动

湿实验、临床、田野与硬件研究可接入部分记录，但“零额外手工录入”不列为首期承诺。

OPAL 不承诺代替研究者判断何为真；它承诺使每一个重要判断都可被追问、可被展开、可被重放。
02

问题：执行成本下降，责任成本没有

部分计算型科研任务的边际执行成本已显著下降。单个 agent 可在一夜之间完成数百次实验、生成多套分析并起草多个版本；但导师、审稿人与署名者的注意力并未同步扩张。

瓶颈因此从“谁来做”转移到“谁来看、谁来信、谁来负责”。既有质量机制以人月为单位设计，当产出速度提高一个数量级，它们不是变慢，而是失去覆盖率。

最稀缺的资源不是算力，而是一个人能够充分理解并愿意为之签署的关键结论数量。

OPAL 的目标不是把全部监督成本变为常数，而是把人的注意力从上万次执行动作，收敛到少量真正需要判断的 checkpoint 与 material claims。

北极星指标
Signed claims per attention-hour
在给定责任标准下，单个研究者每小时能够充分理解并签署的关键 claim 数量。
优化目标：提高可问责的吞吐量，而非制造更多未经理解的产出。
需要被压低的成本
执行级监督、证据检索、provenance 核对、重复性检查与低层次质量筛查。
execution supervision ≈ O(checkpoints)
scientific judgment ≈ O(material claims)
03

职责分层：把 PI 的工作拆分为六层

这是系统设计的基准面。层序有含义：自上而下，人的参与递减，自动化递增。任何新功能都必须可被指认归属于其中一层，否则不应存在。

TasteLayer 1

选题，判断结果是否重要，决定是否发布以及如何组织叙事。

这是人在系统中存在的核心理由。系统提供信息，但不替代最终的价值判断。

Human
最终负责
PortfolioLayer 2

在算力、预算、时间与注意力约束下，决定测试哪些假设、投入多少、何时止损。

人设定策略与约束，系统执行分配、估值与资源回收。

Human 定策略
System 执行
ExecutionLayer 3

编写代码、运行实验、参数扫描、消融、调试、复现 baseline。

该层将持续商品化。OPAL 不把模型能力本身视为护城河。

Agent
EvidenceLayer 4

将 claim 连回代码版本、数据快照、配置、环境、实际 run 与 artifact。

对计算型 run，provenance 应从研究者无法绕开的执行层被动捕获，不增加额外记录动作。

System
自动捕获
Review & Sign-offLayer 5

系统呈现每个 claim 的证据、限制与自动检查结果；人判断方法是否合理、证据是否充分、结论是否重要，并明确签署。

系统负责缩短核验路径，不负责代替理解。

Human
审阅与签署
MemoryLayer 6

跨项目累积失败记录、死路、可复用组件、异常模式与反复出现的风险。

一个 lab 之所以成其为 lab，而非一组孤立项目，正在于失败与基础设施可以复利。

System
持续累积
04

一个端到端案例

抽象架构只有落到一次真实研究流程中，才能说明人的成本究竟在何处被压缩。

假设：增加推理 token 可显著提高某类组合推理任务的成功率，且存在可预测的饱和区间。
01
Human

写下 falsifier、最大预算 500 GPU-h、最小效应量，以及“连续两个 checkpoint 无改善即停止”的 kill 条件，并签署立项。

02
Agent

在 contract 内生成 48 个配置，复现 baseline，执行多种 token budget 与 seed 组合。

03
Gate

泄漏检查拦截 3 个 run；它们不进入可签署证据集，但完整事件仍被保留。

04
Planner

预算消耗至 60% 时，整体效应量低于阈值，原假设触发 kill，剩余资源被回收。

05
Agent

在失败 run 中识别出一个预先未定义的任务子群。系统不恢复原项目，而是生成待审批的新 hypothesis node。

06
Human

判断该异常是否值得追踪；若批准，则为新节点重新定义 falsifier、预算与 claim 范围。

07
Sign-off

最终仅对“整体假设未获支持”与“特定子群出现待验证信号”两条 material claim 进行审阅与签署。

Agent 迭代：数百次人的强制介入：立项 · 异常分支 · 签署
05

生命周期：一棵会分叉、也会被终止的假设树

科研不能按瀑布模型组织。目标本身需要通过执行去发现；执行过半后发现原假设错误，是常态而非事故。因此立项文件不是 executable specification，而是一棵 living hypothesis tree。

01
Propose

写下 claim、预期证据、falsifier、预算上限与 kill criteria。无法说明何种结果构成失败的假设，不予立项。

02
Approve

人签署立项，同时消耗一份 portfolio 配额与注意力配额。

03
Execute

Agent 在 contract 内迭代。代码、数据、配置、环境与 artifact 进入 append-only event log。

04
Gate

机器检查 baseline、泄漏、方差、预算与预定义统计阈值。Gate 只判定可形式化的条件。

05
Branch

Continue、Pivot、Kill 或 Escalate。每一次 escalate 都消耗独立的注意力预算。

06
Compile

从 evidence graph 生成 claim bundle：证据链、限制、失败 run 与自动检查结果，而非仅生成一段连贯的叙述文字。

07
Sign

人判断方法、支持强度与 significance，并签署 material claims。

Kill 自动执行。任何 override 都不能恢复原项目，只能创建一个具备新证据、新预算与新 falsifier 的子假设。

立项即申请：实验室内部的 grant 机制

一旦假设必须在开工前声明 claim、预期证据、falsifier 与预算上限，Propose 就不再是一份任务描述，而是一份 proposal。这个同构是结构性的，而非修辞：Planner 在固定总盘子下，对一组风险与成本异质的申请做组合配置，正是 program officer 的问题。

Grant 机制OPAL 对象差异所在
Specific aimsclaim + scope + materiality必须机器可求值，而非自然语言目标
Preliminary results已签署的证据链与 lab memory 引用可自动核验，无需信任申请者的自述
Go / no-go criteriafalsifier + kill predicate在 checkpoint 上自动求值，而非年度评审
经费申请budget：GPU-h、wall-clock、token、attention注意力是与算力并列的独立预算
Stage gate / 拨款分期tranche 释放 + Successive Halving预算分配机制与资源调度算法是同一件事
Track recordcalibration：预测成本 / 效应量 vs 实际值可计算的先验，而非评审人的印象
Final reportclaim bundle + sign-off失败 run 与被排除项默认进入记录
 Table 1 · 假设立项与科研资助的同构。把它写明的价值在于：资助机制中已被研究透彻的失效模式，会原样出现在 OPAL 内部。

代价是把 principal–agent 问题请进了实验室内部。当预算需要申请，申请者就有系统性的乐观偏差：低估成本、高估效应量。Agent 会更严重，因为“拿到预算”是它通往任何 reward 的必经之路——这是 metric gaming 的上游版本，发生在尚无任何证据可供核验的阶段。而且 proposal 对 agent 是廉价的：它可以一天生成一百份，于是审批本身成为新的注意力瓶颈，恰是 OPAL 要消灭的东西。

Tranche 释放

不一次性批复全额预算。先释放一档，milestone 达成才释放下一档；这与 §09 的 Successive Halving 是同一机制的两种语言。

Calibration 先验

在 lab memory 中累积每个假设生成策略的预测偏差。长期高估者的申请自动折价，无需人工识别。

Scoring rule

Agent 上报的不是“需要多少预算”，而是“在预算 B 下预期降低多少不确定性”。事后按实际信息增益结算未来配额，使诚实上报成为占优策略。

申请成本

限制并发申请槽位，或令每份 proposal 消耗一份注意力配额。否则廉价申请会淹没审批。

需要守住的边界：真实资助体系恰恰在 OPAL 声称要优化的指标上表现最差——慢、保守、评审注意力受限、奖励增量式安全牌。区别在于人做什么：人不逐份审批，人写 call——设定资助规则（何为 material、何种风险等级可自动放行、单节点预算上限）；Planner 依规则执行 desk reject 与 tranche 释放，仅超出规则的申请升级到人。人的消耗因此是 O(policy)，而非 O(proposals)。
06

证据保证：可追溯不等于自动为真

OPAL 必须明确自身能够保证什么、不能保证什么。证据系统的价值来自边界清晰，而非措辞强度。

L1 · Integrity

完整性

代码、数据、配置和 artifact 的哈希可验证，历史记录不可被静默覆盖。

L2 · Provenance

来源

可确定每个结果由哪个 run、环境、模型、prompt 与工具链产生。

L3 · Reproducibility

可重放

第三方可在规定环境与容差内重新执行关键 run。

L4 · Validity checks

形式化检查

通过预定义的 baseline、泄漏、方差、预算与统计检查。

L5 · Claim support

支持强度

证据是否足以支撑 claim，由机器辅助与人工审阅共同判定。

L6 · Significance

科学意义

结果是否重要、是否值得发布，最终由签署者承担判断责任。

「在预注册的任务子集上，token-to-computation ratio 与成功率呈稳定的 logistic 关系，交叉验证 R² = 0.94。」 ← 证据支持到第几层？

07

控制回路：分离时钟频率，而非把人嵌入每一步

自上而下的目标分解与自下而上的快速迭代并不矛盾。解法是三层不同频率的控制回路：上层下发 contract，下层在边界内自治，仅当 contract 被触发时上层才被唤醒。

天—周
IntentL0 · Human

将 taste 转化为假设树：claim、falsifier、预算、kill criteria、可接受的风险。

人在此处执行高杠杆的少量写操作。

小时
PlannerL1 · System

展开、剪枝、重新定价假设树；分配算力与注意力；签发 contract；在 checkpoint 求值规则。

事件驱动，而非持续把决策推给人。

秒—分钟
AgentL2 · Autonomous

edit → run → observe → repeat。快速试错仅发生在 contract 允许的行动空间内。

越界即停止，不依赖 prompt 中的规劝性表述。

监督带宽来自一个结构性事实：人的介入次数与重要 checkpoint 和 material claims 相关，而与 agent 的每一步迭代无关。

Hypothesis 必须可被机器求值

Hypothesis {
  id, parent
  claim        : { text, scope, materiality }
  falsifier    : 可自动或半自动判定的失败条件
  budget       : { gpu_h, wall_clock, tokens, attention }
  gates        : [ baseline, leakage, variance, preregistered_tests ]
  kill         : 在 checkpoint 上求值的谓词
  override     : 仅允许创建新子节点，不修改历史
  status       : proposed | running | pivoted | killed | signed
}

Contract：交付给 agent 的不是步骤，而是封闭的行动空间

Objective

可计算的 metric 与阈值。不是“把实验做好”，而是明确的评估函数与适用范围。

Budget

GPU-h、wall-clock、token 与外部调用的硬上限。预算续期属于 Planner 决策。

Write scope

可写路径、网络白名单、数据集只读挂载与密钥权限。在 runtime 层强制执行。

Stop condition

达标、预算耗尽、连续 k 次无改进、风险事件或 gate 失败。

Artifact schema

必须产出的 metrics、图表、checkpoint、seed、失败日志与限制说明。

Escalation policy

哪些异常需要人介入，哪些由 Planner 自动处理，以及每次升级消耗多少注意力预算。

08

证据捕获、自动 Gate 与威胁模型

对计算型 run，证据应从研究者无法绕开的执行层被动捕获，而非依赖自觉记录。事件日志是主数据，evidence graph 是可演化的物化视图。

// 起点：建立不可变的执行身份
git      → commit sha + diff；按策略拒绝未登记的工作区
model    → provider / model id / version / decoding params
prompt   → system + user + tool schema 的内容哈希
agent    → tool calls / policy decisions / intermediate artifacts

data     → content-addressed manifest；权限与隐私策略随快照记录
env      → lockfile + container digest + hardware metadata
runner   → run_id；stdout / metrics / artifact hash / 资源用量
store    → append-only event log；签名 checkpoint 不可覆盖
graph    → 从事件日志派生 claim ↔ artifact ↔ run ↔ code/data/config

Gate 只检查机器能够明确判定的事项

Baseline

已知结果重跑并落在预定义容差内。

Leakage

实例、语义近邻与派生数据的交叉检查；高风险信号自动阻断。

Variance

满足预定义的 seed 数、置信区间与稳健性报告要求。

Selective reporting

失败 run、被丢弃的配置与后验改动必须进入完整记录。

Budget & policy

资源、网络、写权限与敏感数据策略越界即停止。

Novelty within memory

与 lab memory 中已测试或已 kill 的假设做相似性检查，避免无意识重复。

Threat 01

Metric gaming

Agent 为达成目标而修改评估脚本、利用数据漏洞或优化代理指标。对策：评估代码只读、独立 evaluator、隐藏测试与策略隔离。

Threat 02

选择性报告

仅保留成功 run，隐藏失败、重试与后验筛选。对策：调度器层记录全部任务，claim bundle 默认展示排除项。

Threat 03

日志与 artifact 被篡改

事后覆盖输出或重写历史。对策：内容寻址、append-only 日志、签名 checkpoint 与外部时间戳。

Threat 04

隐私与数据外传

Agent 通过工具或网络泄露敏感数据。对策：网络白名单、密钥隔离、最小权限，数据策略随 run attestation 记录。

Threat 05

Gate 自身失效

自动检查并非天然可靠。对策：gate 版本化、测试集、独立重放与明确的保证边界。

Threat 06

签署流于形式

签署者可能仅阅读摘要而未真正理解证据。对策：materiality 分级、强制抽查、限制同时开放的签署队列，并记录审阅时间。

Threat 07

预算阶段的乐观偏差

Agent 在申请阶段低估成本、高估效应量，以通过审批——此时尚无证据可核验。对策：tranche 释放、calibration 先验折价、按实际信息增益结算未来配额。

Threat 08

申请淹没审批

Proposal 对 agent 近乎免费，可批量生成，使审批本身成为新的注意力瓶颈。对策：并发申请槽位上限、每份 proposal 消耗注意力配额、依规则自动 desk reject。

09

Portfolio Planner：核心的开放研究问题

资源分配不能被简化为按预估 ROI 排队，因为科研假设的价值与可行性往往在投入之后才显现。其真实形态是：在有限预算下，对一组结构可变、揭示成本各异的未知假设执行 exploration / exploitation，并在恰当时刻止损。

Arm 会分裂

Pivot 会生成新的子假设，候选集合随执行动态变化。问题更接近树上的动态决策，而非固定臂 bandit。

Reveal cost 不均匀

部分假设一小时即可判死，部分需要大量预算才能降低不确定性。优化目标应包含单位预算的信息增益。

存在双重预算

算力与人的注意力是相互独立的约束。每一次 escalate、审阅与签署都必须显式计价。

Reward 非单标量

新颖性、可信度、影响力、复用价值与风险无法稳定压缩为单一分数；策略必须保留多目标结构与人的最终偏好。

预算申报不可核验

申请者的成本函数与成功概率无法被 principal 事前验证。核心问题：如何设计 budget elicitation 机制，使 truthful reporting 成为占优策略（DSIC），并与 tranche 释放、calibration 先验相容。

尚未解决的开放问题

以下问题决定 OPAL 是内部工具、通用基础设施，还是一个过度设计的构想。它们需要通过原型与真实团队验证，而非依靠主张解决。

单个研究者能可靠签署多少 material claims？

监督带宽不能仅以项目数量衡量。需要定义 materiality、最小理解标准、审阅时间与错误率，并在真实工作流中测出上限。

第三方 attestation 的最小充分集合是什么？

完整集群通常无法复制，私有数据亦不能随意外发。需要区分逐位复现、统计复现、可信执行环境与受限数据下的验证等级。

证据捕获的真实摩擦能否接近零？

计算 run 可被动捕获，但 notebook、临时脚本、外部 API 与非确定性硬件会制造缺口。产品红线应由可测量的覆盖率定义。

客户首先为效率付费，还是为责任风险付费？

二者会影响销售对象、合规要求与 MVP 顺序。需要访谈承担签署责任的人，而不仅是最积极使用 agent 的研究者。

当模型开始参与 taste，人的责任如何重新定义？

系统的价值不应依赖“人类品味永远不可替代”这一前提。更稳健的命题是：自主程度越高，需要审计、归因、权限与签署的行为就越多。

OPAL 的目标不是让一个人产出更多，而是让一个人能够为规模化的自主研究真正负责：因为可追踪、可停止、可核验、有人签署，所以可以放开规模。
