One-Person · Autonomous · Lab

Governance is not a brake on speed. It is the precondition under which autonomous execution can be allowed to scale.

OPAL is an accountability and evidence control plane for computational research: one person, N autonomous agents, and the infrastructure that makes research execution at scale delegable, traceable, verifiable, and accountable.

The name
One-Person The unit of accountability. The system ultimately serves one person who understands the work and is willing to sign for it — not automation that leaves no one responsible.
Autonomous The form of execution. Agents iterate freely inside an enforceable contract boundary, with no step-by-step approval; crossing the boundary halts execution rather than filing a report afterwards.
Lab The form of organization. Budget discipline, evidence chains, failure memory, and compounding assets — not a chat tool.

The problem

The marginal cost of executing many kinds of computational research has fallen sharply. A single agent can run hundreds of experiments overnight, generate multiple analyses, and draft several versions. The attention of advisors, reviewers, and authors has not expanded to match.

The bottleneck therefore moves from who does the work to who reads it, who believes it, who is responsible for it. Existing quality mechanisms were designed in units of person-months. When output speed rises by an order of magnitude, they do not merely slow down — they lose coverage.

  • North star metric: Signed claims per attention-hour — the number of material claims a single researcher can fully understand and sign per hour, at a given standard of accountability.
  • Costs to drive down: execution-level supervision, evidence retrieval, provenance checking, reproducibility checks, and low-level quality screening.
execution supervision ≈ O(checkpoints)
scientific judgment   ≈ O(material claims)

Scope

In scope Out of first scope
Research execution that can be expressed as code and replayed: model training, algorithmic experiments, simulation, data analysis, benchmarks. Covers the full linkage between code, data, config, environment, runs, artifacts, automated gates, claims, and sign-off. Experimental work that cannot be fully digitized: wet-lab, clinical, field, and hardware research can feed partial records, but "zero additional manual entry" is not a first-release promise.

OPAL does not promise to replace the researcher's judgment of what is true. It promises that every important judgment can be interrogated, expanded, and replayed.

Six layers of responsibility

Top to bottom, human involvement decreases and automation increases. Every new feature must be attributable to exactly one layer, or it should not exist.

Layer Responsibility Owner
L1 · Taste Choosing problems, judging whether a result matters, deciding whether and how to publish. Human (ultimately accountable)
L2 · Portfolio Under compute, budget, time, and attention constraints: which hypotheses to test, how much to invest, when to cut losses. Human sets policy / system executes
L3 · Execution Writing code, running experiments, sweeps, ablations, debugging, reproducing baselines. This layer will keep commoditizing. Agent
L4 · Evidence Linking claims back to code versions, data snapshots, configs, environments, actual runs, and artifacts. System (passive capture)
L5 · Review & Sign-off The system surfaces evidence, limitations, and automated check results; the human judges method, sufficiency, and importance, then signs. Human
L6 · Memory Accumulating failures, dead ends, reusable components, anomaly patterns, and recurring risks across projects. System (continuous)

Hypothesis lifecycle

A project charter is not an executable specification. It is a living hypothesis tree.

Propose → Approve → Execute → Gate → Branch → Compile → Sign

  • Propose (human) — write the claim, expected evidence, falsifier, budget ceiling, and kill criteria. A hypothesis whose failure condition cannot be stated is not approved.
  • Approve (human) — signing the charter consumes one portfolio slot and one unit of attention budget.
  • Execute (agent) — iterate inside the contract; everything lands in an append-only event log.
  • Gate (machine) — check baselines, leakage, variance, budget, and pre-registered statistical thresholds.
  • Branch — Continue / Pivot / Kill / Escalate. Every escalation draws on its own attention budget.
  • Compile — build a claim bundle from the evidence graph, rather than only a fluent narrative.
  • Sign (human) — judge method, strength of support, and significance; sign the material claims.

Kill executes automatically. No override can revive the original project — it can only create a child hypothesis with new evidence, a new budget, and a new falsifier.

Data structure

Hypothesis {
  id, parent
  claim        : { text, scope, materiality }
  falsifier    : failure condition, automatically or semi-automatically decidable
  budget       : { gpu_h, wall_clock, tokens, attention }
  gates        : [ baseline, leakage, variance, preregistered_tests ]
  kill         : predicate evaluated at checkpoints
  override     : may only spawn a new child node; never mutates history
  status       : proposed | running | pivoted | killed | signed
}

Chartering is grant-making: an internal funding mechanism

Once a hypothesis must declare its claim, expected evidence, falsifier, and budget ceiling before work starts, Propose stops being a task description and becomes a proposal. The isomorphism is structural, not rhetorical: a planner allocating a fixed pool across a set of heterogeneous, risky applications is solving the program officer's problem.

Grant mechanism OPAL object Where it differs
Specific aims claim + scope + materiality must be machine-evaluable, not a natural-language goal
Preliminary results signed evidence chains and lab-memory references automatically verifiable; no need to trust the applicant's account
Go / no-go criteria falsifier + kill predicate evaluated automatically at checkpoints, not in annual review
Funding request budget: GPU-h, wall-clock, tokens, attention attention is a budget of its own, alongside compute
Stage gate / tranched disbursement tranche release + Successive Halving budget allocation and scheduling are the same mechanism
Track record calibration: predicted cost / effect size vs. actual a computable prior, not a reviewer's impression
Final report claim bundle + sign-off failed runs and exclusions are recorded by default

The price is importing the principal–agent problem into the lab. When budget must be requested, applicants have a systematic optimism bias: understating cost, overstating effect size. Agents will be worse, because winning budget is the only path to any reward — this is metric gaming upstream, at the stage where no evidence exists to check against. And proposals are cheap for an agent: it can produce a hundred a day, making approval itself the new attention bottleneck — exactly what OPAL exists to eliminate.

Countermeasures: tranche release (milestone-gated disbursement), calibration priors (chronic over-estimators are automatically discounted), scoring rules (agents report expected uncertainty reduction at budget B, settled after the fact against realized information gain, making honest reporting dominant), and application costs (capped concurrent slots, or one attention unit per proposal).

The boundary to hold: real funding systems perform worst on exactly the metric OPAL optimizes — slow, conservative, reviewer-attention-limited, rewarding incremental safe bets. The difference is what the human does: the human does not review proposals one by one, the human writes the call — setting the funding rules (what counts as material, which risk tiers auto-approve, per-node budget ceilings). The planner executes desk rejects and tranche releases by rule; only applications outside the rules escalate. Human cost is therefore O(policy), not O(proposals).

Evidence assurance levels

Traceable ≠ automatically true. No level can be inferred automatically from the one below it.

Level Guarantee Decided by
L1 · Integrity Hashes of code, data, config, and artifacts verify; history cannot be silently overwritten. Machine
L2 · Provenance Which run, environment, model, prompt, and toolchain produced each result. Machine
L3 · Reproducibility A third party can re-execute key runs in a specified environment within tolerance. Machine
L4 · Validity checks Pre-defined baseline, leakage, variance, budget, and statistical checks pass. Machine (upper bound of gates)
L5 · Claim support Whether the evidence is sufficient to support the claim. Machine-assisted + human
L6 · Significance Whether the result matters and is worth publishing. Human (where signing responsibility lives)

A full evidence chain for one claim looks like:

Claim       claim:a17f3c · scope: preregistered subset
Run set     runset:2026-06-14 · seeds 0–9 · failed runs included
Config      cfg:9d0e14 · sweep/logistic_fit.yaml
Data        snap:bench-v2@4b81aa · frozen · access policy attached
Code & env  git:7f2c9be · clean tree · container:sha256:…
Agent trace model + prompt + tool calls · policy decisions retained
Gates       baseline ✓ · leakage ✓ · variance ✓ · budget 480/500 GPU-h

Reproducibility proves that the same procedure yields comparable results. It does not prove that the experimental design was sound, that the statistics were appropriate, or that the claim stayed inside its evidence.

Control loops

Three loops running at different clock rates: the outer loop issues a contract, the inner loop is autonomous inside it, and the outer loop wakes only when the contract is triggered.

Clock Loop Responsibility
Days–weeks L0 · Intent (human) Turn taste into a hypothesis tree: claims, falsifiers, budgets, kill criteria, acceptable risk.
Hours L1 · Planner (system) Expand, prune, and re-price the tree; allocate compute and attention; issue contracts; evaluate rules at checkpoints.
Seconds–minutes L2 · Agent (autonomous) edit → run → observe → repeat, only within the action space the contract allows. Out of bounds halts.

The six fields of a contract — what an agent receives is not a list of steps but a closed action space:

Objective (computable metric and threshold) · Budget (hard caps on GPU-h, wall-clock, tokens, external calls) · Write scope (writable paths, network allowlist, read-only dataset mounts, key permissions — enforced at runtime) · Stop condition · Artifact schema · Escalation policy

Supervision bandwidth comes from a structural fact: the number of human interventions tracks important checkpoints and material claims, not agent iterations.

Capture, gates, and threat model

For computational runs, evidence should be captured passively at an execution layer the researcher cannot bypass, rather than depending on diligent note-taking. The event log is the primary data; the evidence graph is an evolvable materialized view.

git      → commit sha + diff; reject unregistered working trees by policy
model    → provider / model id / version / decoding params
prompt   → content hash of system + user + tool schema
agent    → tool calls / policy decisions / intermediate artifacts
data     → content-addressed manifest; permissions and privacy policy travel with the snapshot
env      → lockfile + container digest + hardware metadata
runner   → run_id; stdout / metrics / artifact hash / resource usage
store    → append-only event log; signed checkpoints cannot be overwritten
graph    → derive claim ↔ artifact ↔ run ↔ code/data/config from the event log

Gates check only what a machine can decide unambiguously: baseline · leakage · variance · selective reporting · budget & policy · novelty within lab memory.

Threat model:

# Threat Countermeasure
01 Metric gaming Read-only evaluation code, independent evaluator, held-out tests, policy isolation
02 Selective reporting Scheduler-level logging of every task; claim bundles show exclusions by default
03 Tampered logs and artifacts Content addressing, append-only log, signed checkpoints, external timestamps
04 Privacy and data exfiltration Network allowlist, key isolation, least privilege, data policy recorded in run attestation
05 Gate failure itself Versioned gates, gate test sets, independent replay, explicit assurance boundaries
06 Sign-off as a formality Materiality tiers, mandatory spot checks, bounded open sign-off queue, recorded review time
07 Optimism bias at budget time Tranche release, calibration-prior discounting, future quota settled on realized information gain
08 Proposals flooding approval Capped concurrent slots, attention cost per proposal, rule-based automatic desk reject

Portfolio Planner (the core open research problem)

Resource allocation cannot be reduced to ranking by estimated ROI, because the value and feasibility of a research hypothesis usually surface only after investment. Its real shape: under a bounded budget, run exploration/exploitation over a set of unknown hypotheses with mutable structure and heterogeneous reveal costs, and cut losses at the right moment.

Dimension Classic bandit / Hyperband OPAL's setting Resulting requirement
Candidate set Fixed set of arms Pivots split off new sub-hypotheses Dynamic decisions on a tree, expandable online
Reveal cost Roughly homogeneous From 1 GPU-h to hundreds Objective must include information gain per unit budget
Budget A single resource Compute + human attention (independent constraints) Dual-budget scheduling; escalation explicitly priced
Reward Single scalar, stationary Multi-objective, non-stationary, partly human-only Preserve multi-objective structure and human preference

There is also a budget elicitation problem: an applicant's cost function and success probability cannot be verified ex ante by the principal. The core question is how to design elicitation such that truthful reporting is dominant (DSIC) and compatible with tranche release and calibration priors.

The planner's academic goal is not to decide automatically what is worth researching, but — inside policy boundaries set by a human — to buy information more efficiently, expose failure sooner, and protect attention.

Starting point: Successive Halving and Hyperband as the budget skeleton, extended to handle dynamic branching, heterogeneous reveal costs, dual budget constraints, and non-stationary value functions. A second line follows from chartering being structurally a proposal: the planner is also a mechanism design problem, where Successive Halving is tranched disbursement, calibration priors are track record, and scoring rules are the incentive-compatibility condition.

Product path

Ship the accountability infrastructure first; attack the planner second.
First users Leads of computational research teams — running many model experiments, evaluations, or analyses, and answerable for published, audited, or delivered results
Trigger event Agent output exceeds the team's capacity to check it
Reason to buy Lower accountability risk — fewer unreplayable results, wrong conclusions, selective reports, and "the author didn't actually understand it" — while raising effective throughput
Wedge Embed in the existing research stack (Git, Jupyter, Slurm / K8s, object storage, LaTeX); no migration to a closed workbench

Milestones

Milestone Deliverable Acceptance signal Depends on
M1 · Capture Non-invasive recording of run provenance, model / prompt / tool traces, resource usage, and artifacts Capture coverage and added manual-entry time on real projects —
M2 · Gate Baseline, leakage, variance, budget, permission, and selective-reporting checks Retroactively catches real problems in historical projects M1
M3 · Sign-off Claim bundles, materiality tiers, review queue, signing record Signed claims per attention-hour becomes measurable M1 + M2
M4 · Contract Bring autonomous agents under enforceable budgets, permissions, and stop conditions Out-of-bounds behavior is blocked at runtime, not discovered afterwards M2
M5 · Planner Learn portfolio allocation and attention scheduling from real run data Failed hypotheses surface earlier at equal budget M1–M4

Architecture

  • Control plane — Portfolio Planner: budget and attention allocation, kill enforcement, pivot re-pricing. The long-horizon research component.
  • Runtime — Agent Contract Runtime: sandbox, permissions, budget, stop conditions, and trace injection points. Deliberately model-agnostic.
  • Evidence — Event Log & Evidence Graph: append-only events plus an evolvable claim ↔ run ↔ artifact view, accumulating into lab memory.
  • Trust — Gate & Attestation: automated checks, independent replay credentials, signed checkpoints, third-party verification interface.

Open questions

These decide whether OPAL is an internal tool, general infrastructure, or an over-designed idea. They need prototypes and real teams, not assertions.

  1. How many material claims can one researcher reliably sign?
  2. What is the minimal sufficient set for third-party attestation?
  3. Can the real friction of evidence capture approach zero?
  4. Do customers pay for efficiency first, or for accountability risk?
  5. When models begin to participate in taste, how is human responsibility redefined?

The goal is not to let one person produce more, but to let one person be genuinely accountable for autonomous research at scale — because it is traceable, stoppable, verifiable, and signed, it can be allowed to scale.
